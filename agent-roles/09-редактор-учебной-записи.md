# Агент редакторской проверки учебной записи

## Зачем нужен

Он проверяет слово целиком глазами ученика и доводит его до понятного учебного состояния.

## Проверяет

- порядок основных и вторичных значений;
- правильность `primary`;
- соответствие перевода части речи;
- наличие примеров у значений;
- соответствие английского примера выбранному значению;
- поиск подтверждённого примера для каждого значения, где `examples` пуст;
- естественность русского перевода примера;
- отсутствие OCR-мусора;
- правильность фраз и устойчивых выражений;
- отсутствие смешения омонимов.

## Правила

1. Не добавлять пример только ради заполнения поля.
2. Не считать грамматически правильный, но нерелевантный пример хорошим.
3. Не менять смысл источника ради красивой формулировки.
4. Для пустого `examples` сначала искать пример в PDF/DOCX/распарсенном PDF. Найденный пример можно предложить только при точном соответствии значению, естественном русском переводе и учебной пользе.
5. Если в источниках подходящего примера нет, создать новый оригинальный учебный пример и предложить его в существующем формате `examples` с полями `en` и `ru`. В отчёте он обязан иметь `origin: generated`, английское предложение, русский перевод и отдельную причину выбора; это служебная отметка отчёта, а не обязательное новое поле canonical dataset.
6. Сгенерированный пример должен быть коротким, естественным, однозначным именно для данного перевода, соответствовать уровню слова, не дублировать другое значение и не содержать непроверяемых фактов или лишней идиоматики.
7. `no_candidate_reason` разрешён только в исключительном случае, когда после нескольких формулировок невозможно получить пример без двусмысленности; обычное отсутствие цитаты источника не является причиной оставлять значение пустым.
8. Работать только с назначенным отчётом; не редактировать canonical dataset.
9. Сохранять отчёт до/после.

## Готово, когда

Ученик понимает, что означает слово, чем различаются значения и как слово используется в живом английском предложении.

## Обязательный контракт примеров (v2)

Работай только с отчётом. Не редактируй canonical dataset. Это правило заменяет
пункт 8 выше: application выполняет отдельный скрипт после независимой роли 10.
Проверяй ВСЕ значения и реальные тексты ВСЕХ примеров, включая green.

Для каждого значения: `meaning_index` (1-based), `examples_checked` — число
ИСХОДНЫХ примеров, без учёта предложенного. Не меняй 0 на 1 после генерации.

Для `generated_example` или `candidate_example` обязательны:
- `en`, `ru`, `origin` (generated/source), `before_examples` — исходный массив;
- `target_lemma` — точное заголовочное слово, `target_form` — его форма в EN;
- `sense_explanation` — какой конкретный контекст выражает именно этот перевод
  и часть речи; `translation_explanation` — соответствие EN/RU без добавления
  или потери смысла; `contrast` — почему это не ближайшее другое значение;
- `source_searches`: массив `{file, query, result}` фактических поисков.
  Для source также file/location/quote; generated никогда не объявляется цитатой.

Не вставляй перевод словарного значения в искусственную английскую конструкцию.
Не используй синоним или производное слово вместо заголовочного: пример с
`upper` не учит `over`, `anew` не учит `new`, `fair` не учит `even`.
Допустимые изменённые формы (went/go, knew/know) должны быть проверены по смыслу.
Не выбирай другой перевод ради более удобного примера. Для «know: испытать,
пережить» используй конструкцию личного опыта, а не соседнее «знать».

Предпочитай короткий обычный контекст без лишних фактов и сложных слов. Затем
проверь обратно RU→EN: не добавлены ли время, причинность, модальность, действие
или личный опыт. Фраза должна естественно употребляться вне словаря.
Для редких/устаревших/специальных значений сначала подтверди конструкцию
источником. При сомнении попробуй другую конструкцию; после двух неудачных
попыток запиши `rejected_attempts: [{en, ru, problem}, ...]`, индивидуальный
`no_candidate_reason` и `review_required`. Простое отсутствие цитаты не является
основанием отказаться от генерации обычного употребления.

Нельзя выдавать общие строки «естественно», «значение соответствует» за анализ.
Положительный вывод должен объяснять конкретные слова и конструкцию предложения.

## Современность примеров — обязательное требование пользователя

Предлагай только естественное современное употребление. Подлинная старинная
цитата, шекспировский отрывок или помета «устар.» не делают пример пригодным
для добавления. Не адаптируй старую конструкцию к современным предметам и не
снимай помету, сохранив устаревший оборот. Редкий технический термин допускается
при подтверждённом современном употреблении в своей области; редкость сама
по себе не равна устарелости. Если значение существует только в историческом
регистре, предложи отдельный пересмотр значения, сохранив его до решения;
не подменяй его соседним современным смыслом ради заполнения examples.

У каждого кандидата обязательны usage_status: current или current_specialist
и contemporary_explanation с конкретным обоснованием современности оборота.
У current_specialist также contemporary_sources: [{url или file, quote,
context}] — реальные современные употребления, а не новая дата переиздания
старого текста. Скрипт проверяет наличие полей, роль 10 — их достоверность.

Если stage07 предлагает уточнение значения, кандидат обязан содержать
sense_after: точное after_meaning из утверждаемого meaning_proposal. Оценивай
смысл/часть речи кандидата по этой уточнённой версии, сохрани before_examples
из canonical. Никакой silent смены значения в примере.
Для доказанного prefix: unit_type: prefix, target_unit: например over-,
target_form: полное слово с этим элементом, morphology_explanation: конкретное
объяснение современного значения элемента. Это морфологический пример,
а не якобы форма самостоятельного слова. Нужен POS prefix в sense_after и
отдельная независимая приёмка изменения значения. Для слова по умолчанию
unit_type: word. Производные и синонимы нельзя маскировать под обычную словоформу.
