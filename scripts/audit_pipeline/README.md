# Strict audit pipeline

## Resource measurement and safe phrase appends

`python3 -B scripts/audit_pipeline/measure_run.py REPORT_ROOT --output METRICS.json`
reports recorded CLI usage and exact duplicate snapshot bytes. Archived copies
of the same event log are counted once. Missing usage is explicitly flagged;
totals are incomplete when any attempt lacks usage. Managing-chat tokens are
outside this scope, and bytes are never treated as tokens.

Worker requests omit optional JSON whitespace without removing content.
Multiple `add /phrases/-` operations append distinct elements. Conflict checks
use concrete array indices; editing the same newly appended element is still
rejected. The first explicit append can initialize an absent optional phrases
array, without changing the before snapshot. Duplicate phrase IDs, deletion,
and replacement of existing examples remain prohibited.

`validate_stage.py` проверяет обязательные поля, evidence и неповторяющиеся причины. `validate_reports.py` — обязательный финальный gate для всех партий 06–10: он проверяет реальные файлы источников, страницы/строки, цитаты, `before/after`, `primary`, уникальность evidence и причины, а также запускает dataset QA.

Проверка полного отчётного корня:

```bash
python3 scripts/audit_pipeline/validate_reports.py \
  dictionary_audit_cycles/strict_2026-10-26 \
  --run-final-qa
```

Для частичного корня указывается смещение в dataset, например `--start-index 1000` для слов 1001–2000. Любой ненулевой код завершения означает, что отчёт нельзя принимать.

`apply_manifest.py` применяет только подтверждённые текстовые изменения после проверки `before`.

Для запуска пяти независимых ролей используйте `dispatch_roles.py`. Worker
получает JSON-вход, включающий роль, текущие 20 записей и результаты предыдущих
этапов, и обязан записать один JSON-массив из 20 записей:

```bash
python3 scripts/audit_pipeline/dispatch_roles.py \
  --batch-index 1 \
  --output-root dictionary_audit_cycles/strict_run \
  --worker "python3 scripts/audit_pipeline/codex_worker_adapter.py"
```

Worker получает параметры `--role`, `--input` и `--output`. Dispatcher не
создаёт заменяющие данные: отсутствие output, неверный JSON, неверное число
записей или провал финального gate останавливают партию.

Dispatcher кэширует каждый stage по хешу роли, входных записей и предыдущих
JSON-результатов в `.dispatch_cache.json`. Повторный запуск той же партии не
вызывает модель повторно; используйте `--force` только после изменения prompt,
источников или при намеренной перепроверке.

После stage 06 dispatcher создаёт `classification.json` с классами:

- `green` — явной смысловой причины для model-pass не найдено;
- `yellow` — есть пустые примеры, generated/no-candidate или неполное evidence;
- `red` — структурная проблема или уже установленный `review_required`.

Классификация не принимает запись автоматически. Она только позволяет worker-у
сократить model-pass для green и направить больше reasoning на yellow/red.

Перед вызовом первой роли dispatcher запускает `preflight_batch.py`. Он
механически фиксирует 20 слов, порядок canonical dataset, список локальных
источников, пределы страниц PDF и значения без примеров. Он не выбирает
основное значение и не переставляет meanings: порядок основных значений и
`primary` остаются смысловой задачей ролей 06/08.

Локальный адаптер `codex_worker_adapter.py` запускает каждый этап через Codex
CLI в режиме `read-only` и применяет `role_output.schema.json` к ответу модели.

Сначала генерируйте результаты ролей по `ONE_PROMPT.md`, затем валидируйте каждый JSON и только после этого применяйте manifest.

Для отдельной проверки самых частотных слов сначала используйте
`prepare_selected_batches.py`. Он сортирует только по `frequency_rank` с
детерминированным tie-break по исходному индексу и сохраняет исходный
`dataset_index`; это не меняет canonical dataset и не подменяет смысловую
проверку порядка значений.

## Приёмка примеров v2

Роли 09/10 получают полный canonical entry и все тексты примеров независимо от
класса green. Классификатор не освобождает от смысловой проверки. Stage 09
пишет предложение, role 10 отдельно судит о семи критериях. Hash связывает
вердикт с точным EN/RU, конкретным значением, исходными примерами и пояснениями.
Изменение любого из этих данных требует новой приёмки. Схема контракта описана
в role 09/10; `example_contract.py` проверяет связи и полноту, а не английский.

После gate для партии:

```bash
python3 scripts/audit_pipeline/build_examples_manifest.py REPORT_BATCH manifest.json
python3 scripts/audit_pipeline/apply_examples_manifest.py src/data/oxford_5000.json manifest.json BACKUP --review-batch REPORT_BATCH --dry-run
```

Без `--dry-run` применяются только те же одобренные изменения с совпадающим
before. Произвольный manifest, устаревшая приёмка, «принято без изменения» и
отсутствующий independent review запрещают применение. Существующие примеры
этот инструмент не перезаписывает. Старый apply_quality_fix_manifest отключён;
он позволял применять самоназванные «изменить» без независимой приёмки.
Исторические отчёты без контракта v2 не являются разрешением на новые изменения.
Кэш теперь проверяет и hash выходного stage. Gate dispatcher проверяет только
текущую партию с её правильным смещением.

Остаётся смысловое ограничение: модель может ошибаться даже при полном JSON.
Поэтому важны содержательная независимая критика, поиск конструкции для редких
значений и явный review_required после неудачных попыток. Нельзя обещать
идеальный язык на основании нуля структурных ошибок.

Для инструментального worker-а без shell API вызовов dispatcher поддерживает
`--prepare-stage 06` (затем 07…10). Он создаёт только запрос роли; внешний
изолированный worker записывает назначенный stage JSON. Следующая роль
подготавливается только при наличии предыдущих JSON в правильном порядке.
Для несмежной выборки можно передать `--selected-list` с canonical
`dataset_index`/`word`. Это метаданные выборки, не копия словаря.

Современность обязательна дополнительно к семи исходным критериям: восьмой
judgment contemporary_usage. Для редкого действующего профессионального
употребления автор указывает конкретный современный источник/context;
переиздание старого словаря и помета «устар.» не разрешают применение.
Пустые значения и кандидаты, отклонённые по современности/смыслу, остаются
review_required. Одобренный пример другого значения того же слова можно
применить отдельно: отказ не переносится автоматически на всё слово.

## Уточнение определения вместе с примером

Stage07 meaning_proposals хранят полные before_meaning/after_meaning, источники
и причину. Разрешены только translation/partOfSpeech/register; id, primary,
порядок и старые примеры сохраняются. Stage10 отдельно принимает каждое
определение через meaning_reviews с пятью содержательными критериями и hash
всего предложения, включая источники. Новый пример связан с точным sense_after.

Тот же build_examples_manifest.py формирует совместный manifest. Тот же
apply_examples_manifest.py применяет определение и одобренный пример одной
операцией с final QA и откатом. Ошибочное определение блокирует связанный
пример. Одобрённое уточнение с честной исторической пометой может быть принято
без старинного примера; пустое поле не заполняется любой ценой.

Для документированного словообразовательного элемента допускается POS prefix
и явный unit_type prefix: целое производное в примере не объявляется обычной
словоформой заголовочного слова. Это требует отдельной морфологической
проверки роли10. Структура canonical meanings сохраняется.

## Усиление проверок 2026-11-03

Изменения, команды проверки и ограничения описаны в [WORKFLOW_REVIEW.md](WORKFLOW_REVIEW.md).
Dispatcher передаёт полные записи всем ролям и проверяет каждый этап до передачи следующему агенту.
Для омографов нужен явный `dataset_index` в `selected_indices.json`; неоднозначный выбор по одному слову запрещён.
Отчёты должны содержать поиск по каждому доступному источнику и цитаты, реально присутствующие по указанным координатам.

## Механический поиск источников

Перед запуском роли dispatcher создаёт `source_search.json`: для каждого слова
проверяются все PDF/DOCX в корне проекта. Извлечение использует pdftotext либо
macOS PDFKit; DOCX читается через XML. Кэш `tmp/audit_source_cache` хранит текст
источников, а не копию словаря; SHA-256 исходника и версия экстрактора управляют
повторным использованием. Пустые страницы явно перечислены. Полностью пустое
извлечение останавливает подготовку и требует OCR.

В пакет входят до трёх коротких совпадений на слово/источник, общее число
совпадений и признак усечения. Приоритет совпадения в начале строки — только
лексическая эвристика, не выбор значения. Агент обязан оценить смысл и при
необходимости прочитать полный контекст. Отрицательный буквальный поиск не
исключает ошибки OCR, переносы или другие формы слова.

Адаптер предоставляет исходники и кэш ссылками в read-only окружении, без
повторного копирования книг. Агенту доступен вспомогательный скрипт:

```sh
python3 source_search.py --cache-file source_cache_0.json --location 123
python3 source_search.py --cache-file source_cache_0.json --word 'used to' --limit 10
```

Подготовку можно выполнить отдельно, без модели:

```sh
python3 -B scripts/audit_pipeline/source_search.py --selected-list PATH/selected_words.json --output PATH/source_search.json
```

Пакет не заменяет отчёты 06–10 и не разрешает изменение словаря. Новые результаты
поиска входят в fingerprint dispatcher через хеш пакета, чтобы изменения источников
не переиспользовали старый ответ агента.

### Исправление отклонённого этапа

`dispatch_roles.py --repair-stage 06` передаёт агенту прежний отчёт и ошибки
общего gate вместе с обычным запросом. Все 20 записей возвращаются заново;
прошедшие проверки не означают автоматического одобрения смысла. Прежний
отчёт и события CLI сохраняются в `repair_06_NNN/`. Новый отчёт проходит тот
же gate. При новой ошибке выполнение останавливается; бесконечных повторов нет.

Этот режим сокращает повторное исследование, но требует измерения расхода:
полный ответ всё ещё генерируется заново. confidence назначает агент, а не
таблица автоматического перевода слов «высокая/средняя» в числа.

Совместимость формата качества: отдельные sense_explanation, translation_explanation, contrast и contemporary_explanation принимаются gate как развёрнутые пояснения качества. Не дублируй их в quality_checks. Для generated_example также обязательна отдельная reason. Независимые judgments роли 10 остаются обязательными.

## Формат точечных ответов v2

Dispatcher и worker сохраняют ровно 20 записей в заданном порядке. Модель
возвращает компактный JSON; `run_worker` сохраняет его как `stage_NN.wire.json`,
затем `report_delta.expand_records` собирает обычный `stage_NN.json`. Все gates
и независимые агенты получают полный восстановленный отчёт. Сам сборщик не
назначает confidence, причины, цитаты, семантические оценки или решения.

### Роль 07

`before` и `after` можно не возвращать: before берётся из текущих 20 входных
записей, after строится только из явных предложений. Для обычного изменения
значения сохраняются `meaning_index` (1-based), reason, sources; вместо
before_meaning/after_meaning можно вернуть:

```json
{"edits":[{"op":"replace","path":"/translation","before":"старый перевод","after":"новый перевод"}]}
```

Если требуется одновременно изменить значение и фразу, используйте одну
`entry_proposals` группу на слово вместо meaning_proposals:

```json
{
  "reason":"Почему части изменения связаны",
  "confidence":0.95,
  "edits":[
    {"op":"replace","path":"/meanings/0/translation","before":"старый перевод","after":"новый перевод","reason":"Обоснование этой правки","sources":[{"file":"source.pdf","page":1,"quote":"Точная цитата"}]},
    {"op":"replace","path":"/phrases/0/translation","before":"старый перевод фразы","after":"новый перевод фразы","reason":"Обоснование связанной правки","sources":[{"file":"source.pdf","page":1,"quote":"Точная цитата фразы"}]}
  ]
}
```

Пути RFC6901 используют **zero-based** индексы; meaning_index отчётов остаётся
**one-based**. Разрешены translation, partOfSpeech, register существующих
значений/фраз и добавление новой полной фразы через `/phrases/-`. У новой фразы
нужен уникальный id и пустой examples. Удаление, изменение ID, перестановки,
primary и замена примеров этим контрактом не разрешены. Для них нельзя
использовать обход через замену всей записи.

Роль 10 получает `entry_bindings` и возвращает `entry_reviews` с точным hash,
verdict, confidence и отдельными judgments source_support, translation_accuracy,
part_of_speech_accuracy, information_preserved, disposition. Каждое содержит
pass и индивидуальную reason. Изменение любой части группы делает старую
приёмку недействительной. Если группа отклонена, её части не применяются.
Примеры также проходят свой неизменённый независимый контракт; существующие
примеры не перезаписываются. Запись файла производится через временный файл и
атомарную замену; при ошибке QA исходные байты восстанавливаются.

### Исправления любого этапа

При `--repair-stage NN` для каждого из 20 слов возвращается только:

```json
{"word":"word","base_sha256":"из repair.base_hashes","edits":[]}
```

Пустой edits сохраняет запись без изменений. Изменённые поля передаются
операциями add/replace с точным before для replace. Сборщик проверяет hash,
предусловия, запрет перекрывающихся путей и идентичность слова. Для этапа 07
исправляются предложения, а не собранные before/after. Полный отчёт вновь
проходит те же gates. Прежние ответы и статистика сохраняются в repair_NN_XXX.

### Адреса замечаний роли 10

Помимо существующего meaning_index разрешён `target`:

- `{kind:"meaning", index:1}` или `{kind:"phrase", index:1}` — существующий элемент;
- `{kind:"field", path:"/phon_br"}` — существующее поле;
- `{kind:"missing_meaning", description:"конкретно какое значение отсутствует"}`.

Обязательны problem и required_action. Null meaning_index без явного target
по-прежнему отклоняется. Скрипт не угадывает адрес замечания по его тексту.

Старые отчёты с неподтверждёнными правками вне meaning_proposals остаются
отклонёнными. Их решения нельзя автоматически переносить на новые группы:
агент должен явно оформить связи, а независимая роль — принять новый hash.

### Повторный запуск и независимые дополнения

`--start-stage NN` переиспользует предыдущие этапы только после проверки входных записей, инструкций и source packet. Для 08/09 дополнительно проверяется неизменность after этапа 07. `--stop-after NN` завершает частичный прогон и не означает приёмку всей партии.

Для исправления только partOfSpeech существующей фразы допускается пустой sources: доказательством служат неизменённый текст фразы, конкретное синтаксическое обоснование и независимая приёмка роли 10. Если изменяется сама фраза или перевод, это исключение не действует.

Неодобренная атомарная группа блокирует зависимые примеры, но не независимые одобренные дополнения к неизменённым значениям. Предложения заменить существующие примеры не применяются текущим контрактом и перечисляются в manifest.deferred.json вместе с зависимыми уточнениями.
